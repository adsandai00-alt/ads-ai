# ADS & AI RAG Chatbot

A small Retrieval-Augmented Generation (RAG) chatbot embedded in the ADS & AI website. It answers questions from **students** (about the programme and project types) and from **companies** (about what makes a good assignment, with an optional sanity check of a described idea against our requirements). Bilingual: Dutch + English, auto-detected.

This is the **initial setup** — local-only, no public hosting yet, no real assignments dataset yet. Everything is designed to be incrementally improved.

---

## 1. Architecture

```
Browser (index.html + script.js chat widget)
        │  POST /chat  { message, user_type, session_id, lang? }
        ▼
FastAPI on http://localhost:8000  (app.py)
        │  langdetect → pick system prompt (student|company × nl|en)
        │  embed query → ChromaDB top-k retrieval (rag.py)
        ▼
OpenAI gpt-4o-mini  ──►  reply + sources
```

| Component | Choice | Where |
|---|---|---|
| Chat LLM | `gpt-4o-mini` | `rag.py` |
| Embeddings | `text-embedding-3-small` | `ingest.py`, `rag.py` |
| Vector DB | ChromaDB (persistent, cosine) | `chroma_db/` |
| Backend | FastAPI + Uvicorn | `app.py` |
| Frontend | Vanilla JS widget injected into the existing site | `../index.html`, `../script.js`, `../styles.css` |
| Knowledge base | 6 Markdown files split on `##` headings | `knowledge/*.md` |
| Session memory | In-process dict, last 6 turns per `session_id` | `app.py` |

## 3. Setup (Windows / PowerShell)

```powershell
# from the repo root
cd chatbot

# 1. virtual env + deps
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt

# 2. configure
copy .env.example .env
# open .env and paste your OpenAI key

# 3. build the vector DB
python ingest.py
# expect:  Indexed ~25 chunks from 6 files into 'ads_ai_kb'.

# 4. start the API
uvicorn app:app --reload --port 8000
```

On macOS / Linux, the only difference is `source .venv/bin/activate` instead of `Activate.ps1`.

### Open the website

Open `../index.html` directly in the browser (or via VS Code Live Server on `http://localhost:5500`). The chatbot button appears bottom-right. CORS is open on `*` so `file://` works during dev.

If you host the frontend on a different origin, set `window.CHATBOT_API_BASE` in a `<script>` tag before `script.js` loads to point at the backend URL.

## 4. Adding or updating knowledge

The knowledge base is plain Markdown — version-controlled, easy to diff.

1. Add or edit a file under `knowledge/` (e.g. add a new FAQ entry as a new `## Heading` block).
2. Re-run `python ingest.py`. It deletes the collection and rebuilds it; the API picks up the new collection on its next request without restart, but a `uvicorn` restart is safest.

**Chunking rule** the ingester applies: each `##` heading starts a new chunk. So:
- Use `##` for each Q&A or topic — that becomes a retrievable unit.
- Keep chunks roughly 100–800 tokens. Very long sections will still work but retrieval is sharper when chunks are focused.
- The file's first `#` title is used as the heading for the intro region (the text before the first `##`).

## 5. Testing

Run from `chatbot/`:

```powershell
pytest
```

Three layers of tests:

### a) Unit / file-loading

`tests/test_retrieval.py::test_eval_file_loads` — the eval JSON parses and has the required keys. Runs without API access.

### b) Retrieval quality (gold set)

`tests/eval_questions.json` holds ~15 questions (Dutch + English, both roles). Each question lists the markdown file we expect the retriever to surface. Two tests:

- `test_retrieval_surfaces_expected_source[<id>]` — for each question, the expected file is in the top-4 retrieved chunks.
- `test_retrieval_topk_hit_rate` — overall hit rate must be ≥ 80%. Prints the actual rate to the test log.

When you add knowledge, **also add a question to `eval_questions.json`** that targets it. Treat the eval set as a living regression suite.

### c) Chat smoke tests

`tests/test_chat.py` hits the FastAPI app via `TestClient`:

- Student asks (NL) about project types → reply mentions ML/DL/Autonomous + cites `project_types.md`.
- Company asks (EN) about a good ML assignment → reply mentions dataset + problem definition.
- Out-of-scope question → reply gracefully says it doesn't know or names Mirabai.
- `/reset` clears the session.

Tests skip themselves if `OPENAI_API_KEY` is missing or `chroma_db/` is empty — so a fresh checkout runs the file-load test only, and the suite goes green once you've configured and ingested.

## 6. Improvement loop

In rough priority order. Each one is small enough to do in an afternoon.

### Tune retrieval
- **Chunk size.** Split very long `##` sections into `###` sub-chunks (extend `_HEADING_RE` in `ingest.py`). Watch the hit rate change in `test_retrieval_topk_hit_rate`.
- **Top-k.** Increase `TOP_K` in `.env` from 4 to 6 — usually trades a bit of latency / tokens for better recall.
- **Hybrid search.** Add `rank_bm25` and fuse BM25 scores with Chroma's cosine ranking. ChromaDB also supports `where_document` for keyword filtering.
- **Reranker.** Retrieve top-20 with embeddings, then rerank with Cohere Rerank or `bge-reranker` and keep top-4. Strong win when KB grows past ~50 chunks.

### Tune generation
- **Prompt iteration.** Edit `prompts.py`. For the company role specifically, add a structured checklist ("Is there a clear problem? Is there a dataset? …") and ask the model to fill it in when the user describes an idea.
- **Temperature.** Currently `0.2`. Lower to `0.0` for stricter grounded answers, raise to `0.4` for more conversational replies.
- **Citations.** The current widget shows sources collapsed under "Bronnen". To inline-cite, change the system prompt to emit `[bron 1]` markers and post-process them in the frontend.

### Quality controls
- **Add a guardrail.** Append to the system prompt: *"If the user asks about a specific assignment or company by name, refuse and point to Mirabai."* — useful once real assignments are in the KB.
- **Faithfulness check.** Periodically sample 20 replies and grade them on (a) grounded in retrieved chunks and (b) language-correct. A 10-minute weekly habit catches most prompt regressions.

### Scale up
- **Persist sessions.** Replace the in-memory dict in `app.py` with SQLite (`sqlite3.connect("sessions.db")`). Needed before exposing publicly.
- **Real assignments dataset.** Add `assignments/*.md` (one file per submitted opdracht) and re-ingest. Add an `assignment` source type tag so the company role can be told *"these are assignments others submitted, use them as examples"*.
- **Submission-to-knowledge pipeline.** Extend the form to also write structured JSON somewhere (Supabase, Firestore, a GitHub PR via Actions). A scheduled job re-runs `ingest.py`.
- **Public hosting.** Move the backend to Render or Railway (free tier). Set `window.CHATBOT_API_BASE` in the HTML. Lock CORS to your domain. Add a per-IP rate limit (`slowapi`).

### Observability
- Log every Q/A with the retrieved chunks to a JSONL file. Re-read it weekly to find: (1) questions with no good source — KB gaps; (2) questions where the answer drifted — prompt issues.

## 7. Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `OPENAI_API_KEY not set` | Copy `.env.example` → `.env` and paste the key. The shell needs to see it; restart your terminal after editing `.env` if needed. |
| `Could not connect to API` in the widget | The FastAPI server is not running, or it's on a different port than `http://localhost:8000`. Override via `window.CHATBOT_API_BASE`. |
| ChromaDB error on first request | You forgot `python ingest.py`. Run it. |
| Retrieval hit rate < 80% | Add or rephrase questions, split long Markdown sections into more `##` chunks, or raise `TOP_K`. |
| Wrong language detected for very short messages | `langdetect` is unreliable on inputs < ~10 chars. The client can override by sending `lang: "nl"` or `"en"` in the request body. |
| Reply mentions a company / assignment by name that isn't in the KB | Hallucination. Lower `temperature` to `0.0`, and reinforce rule #1 ("use ONLY the context") in the system prompt. |

## 8. What's intentionally not here yet

These are deliberate scope cuts for the initial setup, listed so future-you doesn't think they were forgotten:

- No streaming responses (the widget just waits for the full reply).
- No authentication / rate limiting on the API.
- No analytics or logging beyond stdout.
- No specific-assignment knowledge — only program info.
- No CI test job.

All of these are in the **Improvement loop** section as next steps.
